# Архитектура email-конструктора

## 1. Общая схема работы

Система состоит из трёх логических слоёв:

```
┌─────────────────────────────────────────────┐
│  СЛОЙ РЕДАКТОРА (Vue 3)                     │
│  • Дерево блоков                            │
│  • Палитра добавления                       │
│  • Панель опций                             │
│  • Текстовые поля с разметкой               │
│  • Live preview                             │
└─────────────────────────────────────────────┘
                    ↓ (формирует)
┌─────────────────────────────────────────────┐
│  СЛОЙ МОДЕЛИ (JSON)                         │
│  • Структура письма                         │
│  • Опции каждого блока                      │
│  • Текстовый контент                        │
└─────────────────────────────────────────────┘
                    ↓ (передаётся в)
┌─────────────────────────────────────────────┐
│  СЛОЙ РЕНДЕРА (Core JS)                     │
│  • Парсер разметки текста                   │
│  • Рендерер блоков                          │
│  • Контекст вложенности                     │
│  • Валидатор                                │
└─────────────────────────────────────────────┘
                    ↓ (выдаёт)
              HTML-файл + JSON
```

### Поток данных

1. Пользователь добавляет блок через палитру
2. Vue-редактор добавляет узел в JSON-модель
3. Пользователь настраивает опции — модель обновляется
4. Live preview пересчитывает рендер на основе модели
5. Перед экспортом — валидация
6. Генерация финального HTML через core-рендерер
7. Выдача пары файлов: `letter.html` + `letter.json`

## 3. Vue-компоненты редактора

### 3.1. Editor.vue

Главный контейнер, который собирает все части редактора в единую раскладку:

```
┌─────────────────────┬──────────────────────┬───────────────────┐
│  BlockPalette       │  BlockTree           │  BlockInspector   │
│                     │                      │                   │
│  (кнопки добавления)│  (структура письма)  │  (опции блока)    │
└─────────────────────┴──────────────────────┴───────────────────┘
                        │
                        │
        ┌───────────────┴───────────────┐
        │       EmailPreview            │
        │                               │
        │  (визуальный предпросмотр)    │
        │                               │
        └───────────────────────────────┘
```

### 3.2. BlockPalette.vue

Показывает доступные типы блоков для добавления. При клике на блок вызывает добавление в выбранный контейнер или в root.

Список блоков берётся из реестра шаблонов (`templates/index.js`).

### 3.3. BlockTree.vue и BlockTreeItem.vue

`BlockTree` — контейнер, который получает корневой узел из store.

`BlockTreeItem` — рекурсивный компонент для каждого блока. Отображает:
- Название блока
- Кнопки управления: `[↑] [↓] [×]`
- Кнопку `+` для добавления дочернего блока (если шаблон — контейнер)
- Раскрывающийся список дочерних блоков (через рекурсивный вызов себя)

При клике на название блока — устанавливается `selectedBlockId` в store.

### 3.4. BlockInspector.vue

Отображает панель опций выбранного блока. Читает `options` из шаблона и рендерит соответствующие поля:

| type опции | UI-элемент |
|---|---|
| `text` | input |
| `textarea` | textarea |
| `richtext` | textarea для разметки |
| `url` | input с валидацией |
| `select` | dropdown |
| `image` | input + превью |
| `boolean` | checkbox |
| `number` | input type=number |

При изменении значения — обновляется соответствующий prop в модели.

### 3.5. TextField.vue

Используется внутри `BlockInspector` для опций типа `richtext`. Это обычная textarea без WYSIWYG, в которую пользователь пишет текст со своей разметкой.

Под полем может быть краткая справка по синтаксису.

### 3.6. EmailPreview.vue

Получает текущую JSON-модель из store, вызывает core-рендерер и показывает результат в `<iframe>` через `:srcdoc`.

### 3.7. ExportPanel.vue

Кнопка «Экспорт». При нажатии:
1. Запускается валидатор
2. При ошибках — показывается список
3. При успехе — генерируются два файла: `.html` и `.json`

## 4. Core-слой

Независимый JS-модуль, который не зависит от Vue. Может использоваться в Node, CLI или Figma-плагине.

### 4.1. tokens.js

Централизованное хранилище дизайн-токенов:

```js
{
	// Базовый отступ (в пикселях)
	spacing: 16,
	letterSpacing: 0,

	// Основной шрифт
	fontFamily: 'Arial, sans-serif',

	// Цветовая палитра
	colors: {
		text: '#1A1230',
		accent: '#FF0F43', // красный (для важных элементов)
		background: '#ffffff',
		cardBg: '#f5f5f5',
	},

	// Типографика
	typography: {
		h1: { size: 24, lineHeight: 1.3 },
		h2: { size: 20, lineHeight: 1.3 },
		body: { size: 14, lineHeight: 1.3 },
	},
};
```

### 4.2. parser.js
Парсер собственной разметки текста. Преобразует строку с разметкой в HTML с inline-стилями, адаптированный под жесткие требования email-клиентов (без использования семантических тегов).

**Синтаксис разметки**

*Строчные элементы:* 
| Разметка | Результат |
|---|---|
| `**жирный**` | `<b>жирный</b>` |
| `[текст](url)` | `<a href="url" style="...">текст</a>` |
| `{red}текст{/red}` | `<span style="color:#FF0F43;">текст</span>` |
| `{nobr}текст{/nobr}` | `<nobr>текст</nobr>` (для должностей и ФИО) |
| `{br}` | `<br>` |

*Блочные элементы (определяются по началу строки):*
| Разметка | Результат |
|---|---|
| `# Заголовок` | `<span style="...font-size:24px...">` (вместо `<h1>`) |
| `## Заголовок` | `<span style="...font-size:20px...">` (вместо `<h2>`) |
| `- пункт` | элемент `<ul>` |
| `1. пункт` | элемент `<ol>` |

**Правила парсинга:**
- **Отказ от семантики:** Вместо `<p>`, `<h1>`, `<strong>` используются `<span>` с жесткими инлайн-стилями. Это предотвращает margin collapsing и наследование мусорных стилей в Outlook/Gmail.
- **Отступы через `<br>`:** Пустая строка в исходнике превращается в одиночный `<br>` между блоками. Тег `<br>` всегда размещается *внутри* закрывающего `</span>`.
- **Совместимость с типографом:** Функция `escapeHtml` экранирует `<` и `>`, но игнорирует амперсанд `&`, если за ним идут стандартные сущности (`nbsp`, `mdash`, `laquo` и т.д.). Это позволяет безопасно пропускать текст через typograf.ru до парсинга.
- Текст разбивается на строки. Каждая строка классифицируется: заголовок, элемент списка, параграф, `{br}`.
- Смежные `-` объединяются в один `<ul>`. Смежные `1. 2. 3.` объединяются в один `<ol>`.
- Внутри строки парсятся inline-элементы.
- Дефис или цифра в середине строки — обычный текст (не список).
- Незакрытые теги — остаются как литералы (без автоматического закрытия).

### 4.3. context.js

Строит контекст рендеринга для каждого блока. Контекст автоматически рассчитывается при спуске по дереву.

#### Структура контекста

```js
{
  depth: 0,                // уровень вложенности (root = 0)
  contentWidth: 600,       // доступная ширина для контента
  parentType: 'root',      // тип родительского блока
  tokens: { ... }          // дизайн-токены
}
```

#### Логика расчёта

```
Функция buildContext(parentContext, blockType):
  newDepth = parentContext.depth + 1
  newWidth = parentContext.contentWidth - (tokens.spacing * 2)
  
  return {
    ...parentContext,
    depth: newDepth,
    contentWidth: newWidth,
    parentType: blockType
  }
```

#### Пример расчёта

```
root:         depth=0, width=600
  card:       depth=1, width=568 (600 - 32)
    important: depth=2, width=536 (568 - 32)
      button:  depth=3, width=504 (536 - 32)
```

Ширина уменьшается автоматически, шаблон просто использует `ctx.contentWidth`.

### 4.4. renderer.js

Главный рендерер. Принимает JSON-модель письма и возвращает HTML-строку.

#### Алгоритм

1. Создаётся начальный контекст (root, width=600)
2. Для каждого блока верхнего уровня вызывается `renderBlock(node, context)`
3. `renderBlock`:
   - находит шаблон по `node.type`
   - если блок — контейнер, рекурсивно рендерит `children` с обновлённым контекстом
   - если блок содержит `richtext`, парсит текст через parser
   - вызывает `template.render(props, preparedChildren, context)`
4. Собирается полный HTML с `<head>` и обёрткой

### 4.5. validator.js

Проверка JSON перед экспортом.

#### Что проверяется

1. **Обязательные поля** — для каждого блока проверяются опции с `required: true`
2. **Допустимая вложенность** — каждый блок соответствует правилу `allowedParents`
3. **Ссылки** — URL-опции проверяются на валидность
4. **Картинки** — `alt` обязателен для изображений

#### Результат

Возвращает массив объектов:
```js
{ level: 'error' | 'warning', blockId, message }
```

`error` блокирует экспорт, `warning` — только уведомление.

## 5. Система шаблонов

### 5.1. Структура шаблона

Каждый шаблон — это JS-файл со следующей структурой:

```js
export default {
  type: 'уникальный-id-блока',
  title: 'Название для UI',
  category: 'layout' | 'content' | 'service',
  
  options: {
    // схема опций
  },
  
  isContainer: false,           // может ли содержать детей
  allowedChildren: [],          // если контейнер — кого можно класть
  allowedParents: ['root', ...],// куда можно класть
  
  render: (props, children, ctx) => {
    // возвращает HTML-строку
  }
}
```

### 5.2. Реестр шаблонов

`templates/index.js` импортирует все шаблоны и экспортирует объект-карту:

```js
{
  'header': headerTemplate,
  'card-simple': cardSimpleTemplate,
  'button': buttonTemplate,
  ...
}
```

Реестр используется:
- Палитрой — для отображения доступных блоков
- Инспектором — для построения опций
- Рендерером — для поиска шаблона по типу

### 5.3. Принцип разделения шаблонов

**Отдельный шаблон, если:**
- Разная HTML-структура (разные таблицы, колонки)
- Разный набор опций
- Разная логика рендеринга

**Props одного шаблона, если:**
- Разный контент (текст, картинка, цвет)
- Разный вариант оформления в рамках одной структуры

Пример:
- `card-simple` и `card-with-icon` — **разные шаблоны** (разная структура таблицы)
- `button` с вариантами `primary`/`secondary` — **один шаблон**, prop `variant`

## 6. JSON-модель письма

### 6.1. Структура корневого документа

```js
{
  version: 1,
  meta: {
    subject: 'Тема письма',
    preheader: 'Прехедер'
  },
  blocks: [ ... ]     // массив корневых блоков
}
```

### 6.2. Структура блока

```js
{
  id: 'уникальный-id',
  type: 'card-simple',
  props: {
    title: 'Заголовок',
    variant: 'primary'
  },
  content: 'Текст с **разметкой**',  // если шаблон поддерживает
  children: [ ... ]                   // если шаблон — контейнер
}
```

### 6.3. Поля блока

| Поле | Обязательность | Описание |
|---|---|---|
| `id` | Всегда | Уникальный идентификатор для UI |
| `type` | Всегда | Тип из реестра шаблонов |
| `props` | По схеме | Значения опций из шаблона |
| `content` | Если `richtext` | Строка с разметкой |
| `children` | Если контейнер | Массив дочерних блоков |

### 6.4. Пример полного письма

```js
{
  version: 1,
  meta: {
    subject: 'Приглашение',
    preheader: 'Ждём вас на вебинар'
  },
  blocks: [
    {
      id: 'h1',
      type: 'header',
      props: { logo: 'logo.png' }
    },
    {
      id: 'c1',
      type: 'card-simple',
      props: { title: 'Вебинар' },
      children: [
        {
          id: 't1',
          type: 'paragraph',
          content: 'Приглашаем на **важное** событие.{br}Начало в 19:00.'
        },
        {
          id: 'b1',
          type: 'button',
          props: {
            text: 'Зарегистрироваться',
            href: 'https://example.com',
            variant: 'primary'
          }
        }
      ]
    },
    {
      id: 'f1',
      type: 'footer',
      props: { unsubscribeUrl: '{{unsubscribe_url}}' }
    }
  ]
}
```

### 6.5. Работа с ID

- ID присваивается при создании блока (например, `crypto.randomUUID()` или простая функция)
- Используется Vue-редактором для `key` в циклах
- Используется для подсветки выбранного блока в preview
- При экспорте ID можно удалять из HTML, но оставлять в JSON

## 7. Контекст и вложенность

### 7.1. Поток контекста при рендере

```
renderEmail(document)
  ↓
  context = { depth: 0, contentWidth: 600, parentType: 'root', tokens }
  ↓
  для каждого корневого блока:
    renderBlock(block, context)
      ↓
      для контейнеров:
        childContext = buildContext(context, block.type)
        renderBlock(child, childContext) для каждого child
      ↓
      template.render(props, childrenHtml, context)
```

### 7.2. Использование контекста в шаблонах

Шаблон не вычисляет ширину и отступы сам. Он берёт их из `ctx`:

```js
render: (props, children, ctx) => {
  return `
    <table role="presentation" width="${ctx.contentWidth}" cellpadding="0" cellspacing="0" border="0">
      <tr>
        <td style="padding:${ctx.tokens.spacing}px;">
          ${children}
        </td>
      </tr>
    </table>
  `;
}
```

### 7.3. Автоматический пересчёт

При добавлении блока в дерево:
- `depth` увеличивается на 1
- `contentWidth` уменьшается на `spacing * 2`
- `parentType` становится типом родителя

Это обеспечивает консистентные отступы на любом уровне вложенности без ручной настройки.

### 7.4. Контекстные пресеты (опционально)

Если для определённого родителя нужны особые отступы, можно расширить `buildContext`:

```js
if (parentContext.parentType === 'card' && blockType === 'important') {
  // особый случай: important внутри card
  return { ...ctx, spacingMode: 'compact' };
}
```

Но на старте достаточно только базового расчёта по depth.

## 8. Экспорт

### 8.1. Что выдаётся

При нажатии «Экспорт» генерируются два файла:

**`letter-name.html`** — финальный email-HTML:
- Полный документ с `<!DOCTYPE>`, `<head>`, `<body>`
- Inline-стили на всех элементах
- Табличная структура
- Без комментариев, без data-атрибутов, без классов

**`letter-name.json`** — модель письма:
- Полное дерево блоков с ID
- Все опции
- Текстовый контент с разметкой

### 8.2. Процесс экспорта

1. Прочитать JSON-модель из store
2. Запустить валидатор
3. Если есть ошибки — показать список, отменить экспорт
4. Вызвать рендерер — получить HTML
5. Сформировать Blob из HTML и JSON
6. Отдать пользователю для скачивания (два файла в zip или по отдельности)

### 8.3. Импорт JSON

JSON используется в будущем для:
- Повторного открытия письма в редакторе
- Дублирования структуры
- Переноса между пользователями

При импорте:
- JSON парсится
- Проверяется структура
- Загружается в store
- Редактор отображает письмо

## 9. Итоговая архитектура одной схемой

```
                    ┌─────────────────────┐
                    │   templates/*.js    │
                    │   (шаблоны блоков)  │
                    └─────────┬───────────┘
                              │
                              ↓
┌──────────────┐      ┌───────────────┐      ┌──────────────┐
│ BlockPalette │ ───→ │  emailStore   │ ───→ │ email.json   │
└──────────────┘      │  (Pinia)      │      │   (модель)   │
                      └───────┬───────┘      └──────┬───────┘
                              │                     │
         ┌────────────────────┼─────────────────────┤
         ↓                    ↓                     ↓
   ┌───────────┐      ┌──────────────┐      ┌────────────┐
   │BlockTree  │      │BlockInspector│      │  renderer  │
   │  (дерево) │      │  (опции)     │      │  + parser  │
   └───────────┘      └──────────────┘      └─────┬──────┘
                                                   ↓
                                            ┌────────────┐
                                            │EmailPreview│
                                            │  (iframe)  │
                                            └────────────┘
```

Вся система построена вокруг JSON-модели. UI редактирует модель, рендерер потребляет модель, экспорт сохраняет модель. Это обеспечивает единую точку правды и возможность развивать систему в любом направлении без переписывания.
